# Release notes

Write for end users, ordered by importance rather than commit order.

```markdown
# <Product> <version>

_Released <date>_

<One short summary of the release's theme.>

## Highlights

- **<Capability>**: <What users can now do or experience.>

## Improvements

- <Smaller user-visible improvement.>

## Fixes

- <Problem fixed, described as users experienced it.>

## Breaking changes

<Who is affected, what breaks, and the exact migration action.>

## Upgrade notes

<Required upgrade or configuration steps.>
```

Omit empty sections. Never bury breaking changes. Avoid internal file names, implementation jargon, and ticket IDs unless the repository's established release notes use them. Do not turn maintenance work into a user-facing benefit without evidence.
